# 测试验证

## 选择检查

先读取[共用工作约定](../../references/mode-b.md)。从验收标准和差异确定应验证的行为，先查看项目现有测试、脚本及运行说明，再选命令；不要猜包管理器或直接执行未知脚本。

判断测试是否连接生产、删除文件、修改数据库、调用付费接口或执行发布钩子。未确认的外部副作用先调查，必要时改用隔离夹具；高风险动作按共用约定处理。

## 建立证据

- 从最相关、成本合理的检查开始。行为变化需要可判定的正常、边界和失败用例；优先扩展现有测试而非自建另一套框架。
- 回归测试若有必要，确认它能区分修改前后的行为；不会失败的测试不能证明修复。小型文案或格式调整不机械增加测试。
- 按变更影响选择单元、集成、类型检查、构建或端到端验证；只通过构建不能证明业务正确。
- 记录运行目录、命令、环境前提、退出结果和关键观察。日志脱敏，不把成段无关输出塞进交付。
- 失败时区分本次缺陷、原有问题和环境问题。只有必要且低成本时才用基线复现，不覆盖用户改动，不清空环境。
- 修复后重跑相关检查；没有新改动、失败或覆盖缺口时，不无限扩大测试。

## 结果格式

用“通过 / 失败 / 未运行”表达状态，并说明对应行为。失败列出可定位的错误和影响；环境阻塞写出缺少的条件及替代检查。除非用户授权修复，否则只提交验证报告，不顺手改代码。
