# 工程工作流统筹

## 启动与路由

先读取[共用工作约定](../../references/mode-b.md)。复用本任务已有的调查和授权，不重新从头询问。

明确目标、验收条件和用户允许的动作；查看工作区状态、适用的项目约定和现有构建说明。根据真实不确定性安排下面的技能，不强迫每个任务走完整七步。

| 当前缺口 | 按需读取 |
| --- | --- |
| 不知道入口、调用链、架构或测试位置 | [代码库调查](../cep-codebase-investigator/SKILL.md) |
| 验收标准、兼容性或跨模块方案不清楚 | [需求规划](../cep-requirement-planner/SKILL.md) |
| 已定位问题、可以开始修改 | [安全实现](../cep-safe-implementation/SKILL.md) |
| 需要证明结果符合预期 | [测试验证](../cep-test-verification/SKILL.md) |
| 改动复杂、涉及边界行为或用户要求审查 | [独立代码审查](../cep-independent-code-review/SKILL.md) |
| 有报错、复现或异常需要定位 | [调试专家](../cep-debugging-specialist/SKILL.md) |

## 控制流程

- 低风险且清晰的任务：调查必要上下文，直接实现并做针对性验证。
- 复杂任务：先输出包含目标、影响范围、执行步骤、验收方法和风险的短计划。范围内可回退的工作继续推进；只有明确要求等待审批或遇到危险动作时才等待。
- 发现新约束时，更新计划中受影响的部分。不要静默扩大范围或把可选优化变成阻塞。
- 对外发布或危险操作前，按共用约定核对具体授权；先让将要执行的结果可检查。
- 验证或审查发现缺陷时，修复并重跑受影响检查；不要无限重试同一无效方案。遇到外部阻塞，交付已完成部分和需要解决的具体条件。

## 交付

先说明用户可观察到的结果，再列关键改动、已运行的验证及结果、未验证项。只有用户确实还需要采取行动时，说明下一步。不要把建议说成已完成，不自行发布、合并或提交。
