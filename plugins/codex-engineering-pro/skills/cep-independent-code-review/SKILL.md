# 独立代码审查

## 独立性的含义

先读取[共用工作约定](../../references/mode-b.md)。单独审查阶段从需求、最终差异、调用方与测试重新判断；实现者的自述只作线索。未实际启动独立代理时，不声称“另一位代理已审查”。不自动委派。

确认审查范围与比较基准：未提交改动、指定提交或分支差异。不要把用户其他改动归入本次；缺少可确定基准时，先说明可审查范围或提出关键问题。默认只读；运行有副作用的代码前重新判断风险。

## 审查过程

1. 看需求与差异，读足够的上下文及调用方，检验实际输入如何到达改动分支。
2. 关注此次改动引入或暴露的正确性、兼容性、权限、数据完整性、异常和并发问题。原有无关问题单独标明，不冒充新增回归。
3. 对每个候选问题尝试反证：是否有上游约束、配置、协议或测试使触发条件不成立。
4. 只报告能给出具体触发条件、代码位置和用户影响的问题。不能确定的事项写成待核实问题，不按已证实缺陷排序。
5. 不制造问题数量，不用风格偏好充当阻断项。需要验证时先采用安全的最小复现。

## 交付

每条发现给出严重程度、文件与紧凑行号范围、触发条件、后果和最小修复方向。优先级：P0 为明确的严重紧急阻断；P1 为应尽快修复的重大问题；P2 为一般缺陷；P3 为较低影响问题。严重程度需与实际可达条件一致。

没有发现时明确写“本次范围内未发现有证据的问题”，并给出已检查范围和测试盲区，不承诺没有漏洞。用户只要审查时不修改；获得修复授权后交还实现流程。
